# بحث: المنتجات الفعالة وغير الفعالة

> **الحالة: قيد النقاش (2026-09-14).** ماكو أي قرار محسوم بهالملف. كل اللي بي خيارات ومعلومات وتوصيات للنقاش.
> القرارات تنكتب بعدين بـ `docs/items/plan.md`.
> المسارات نسبةً لجذر مشروع waqt، والأرقام بعد `:` أرقام أسطر.

## 1. المطلوب
- **الإخفاء:** المنتج الغير فعال:
  - ما يطلع بالمستقبل عند إضافة منتج لفاتورة شراء.
  - ما يطلع افتراضياً بعرض المنتجات، ولا بأي GET.
- **شروط التعطيل:** مستقبلاً تنضاف شروط تحدد متى ينسمح تعطيل منتج. مثلاً ما ينعطل إذا بيه رصيد.
- **الخوف الأساسي:** الحل ما لازم يعتمد على ذاكرة المطور أو الـ agents. النسيان لازم ما يكسر النظام بصمت.

## 2. الوضع الحالي بالمشروع
- عمود `is_active` نوعه boolean، قيمته الافتراضية `true`، وبدون فهرس (`database/migrations/2026_09_13_230459_create_items_table.php:18`).
- `is_active` موجود بالـ `#[Fillable]` (`app/Models/Item.php:12`)، فأي أحد يكدر يسوي `$item->update(['is_active' => false])`.
- الفورم بيه Toggle يكتب على `is_active` مباشرة (`app/Filament/Resources/Items/Schemas/ItemForm.php:33`).
- الجدول يعرض `is_active` كأيقونة (`app/Filament/Resources/Items/Tables/ItemsTable.php:28`)، وماكو فلتر عليه.
- **ماكو بعد:** فواتير، أوردرات، مخزون، jobs، أو سجل تدقيق (audits).
- **نمط العمليات الموجود:** plan اليوزرز (2.4) اختار Action class لكل عملية. مثاله `SyncUserPermissions` (`app/Permissions/SyncUserPermissions.php:9`)، ويتنادى من الشاشة (`app/Filament/Resources/Users/Pages/EditUser.php:86`).

## 3. معنيين لـ "غير فعال"
- **ما ينختار بعملية جديدة:** قوائم الاختيار، والبحث عند إضافة بند فاتورة، والـ API.
- **ما ينقرا أبداً:** وهذا **غلط**. هاي الأماكن لازم تبقى تشوف المنتج الغير فعال:
  - الفاتورة القديمة، حتى تعرض اسمه.
  - التقارير المالية وحساب المخزون، حتى أرقامها تبقى صحيحة.
  - شاشة الأدمن، حتى المنتج يرجع يتفعل.
- **القاعدة:** مخفي بأماكن الاختيار، ومقروء بكل مكان ثاني.

## 4. طريقة الإخفاء: global scope لو local scope

### 4.1 Global scope
- شلون ينكتب بـ Laravel 13: `#[ScopedBy([ActiveScope::class])]` على الموديل، ويتولد بـ `php artisan make:scope`. نفس طريقة SoftDeletes.
- ينشال بـ `withoutGlobalScope(ActiveScope::class)`.
- **الإيجابيات:** أي query جديدة تخفي غير الفعال تلقائياً.
- **السلبيات، نسيانه بالأماكن المالية يصير صامت:**
  - `Item::sum(...)` بتقرير قيمة المخزن يتجاهل المنتجات الغير فعالة بدون خطأ.
  - `InvoiceItem::whereHas('item')` يشيل بنود الفواتير اللي منتجها غير فعال، لأن الـ scope ينطبق على query العلاقة، فالمجموع يطلع غلط.
  - `$invoiceItem->item` يرجع `null`، فحسابات الكلفة تتخطى البند أو يطلع خطأ.
  - شاشة Filament للمنتجات لازم تشيل الـ scope، وإلا ما ينفع ترجع تفعل منتج.
  - قاعدة `exists` بالـ validation تستخدم query builder مو Eloquent، فالـ scope ما يحميها.

### 4.2 Local scope
- شلون ينكتب بـ Laravel 13: `#[Scope] protected function active(Builder $query): void`، وينادى بـ `Item::active()`.
- **الإيجابيات:**
  - واضح وماكو مفاجآت.
  - العلاقات والتقارير تشوف كل المنتجات بدون استثناءات.
- **السلبيات:** لازم ينكتب بكل مكان اختيار. إذا انسى، المنتج الغير فعال يطلع بالقائمة.

### 4.3 مقارنة النسيان
| الطريقة | إذا نسيت | النتيجة |
|---|---|---|
| Global scope | ما شلته بتقرير أو حساب مخزون | **أرقام مالية غلط بصمت** |
| Local scope بدون حماية عند الحفظ | ما كتبت `active()` بقائمة | المنتج الغير فعال **ينضاف لفاتورة** |
| Local scope ويه حماية عند الحفظ | ما كتبت `active()` بقائمة | المنتج يطلع بالقائمة، بس **الحفظ يرفضه** |

### 4.4 تطور التوصية أثناء النقاش
- **أول توصية:** global scope. السبب جان إن خطأ نسيانه "واضح".
- **بعد مراجعة الدليل الخارجي (القسم 6):** تبين إن أخطاءه بالأماكن المالية صامتة (4.1).
- **التوصية الحالية:** local scope ويه حماية عند الحفظ، لأن نسيانه أرخص (4.3). **مو محسومة.**

## 5. طبقات الحماية حتى ما نعتمد على الذاكرة
1. **الإخفاء بأماكن الاختيار:** بـ `active()`.
2. **الحماية عند الحفظ:** فحص بالسيرفر يرفض المنتج الغير فعال بأي بند فاتورة أو أوردر جديد، مهما جان مصدر الطلب (الشاشة أو API أو كود ثاني). مثال:
   ```php
   Rule::exists('items', 'id')->where('is_active', true)->whereNull('deleted_at')
   ```
   هاي أهم طبقة، لأنها تحمي حتى لو أحد نسى `active()`.
3. **مسار كتابة واحد للتفعيل والتعطيل** (القسم 7).
4. **tests** تكسر إذا أحد، إنسان أو agent، غير القاعدة.
5. **قاعدة مكتوبة للـ agents** بـ `.ai/rules` عن طريق `record-rule`، وتنكتب بس إذا طلبها صاحب المشروع. هاي تذكير، والـ tests هي الضمان.

## 6. الدليل الخارجي: «المواد الفعّالة فقط، نظام بمصنع واحد»
> دليل وصل من صاحب المشروع. مبني على مراجعة آلية `enabled-only` بمشروع الماركتات (`ITEM_ENABLED_SCOPE_REVIEW.md`)، حتى ما تتكرر مشاكلها.

### 6.1 ملخصه
- **الفكرة:** إخفاء الغير فعال افتراضياً فكرة جيدة.
- **لا تفعيل لكل موقع أو مصنع** (JSON أو جدول وسيط)، لأن المصنع واحد.
- **القواعد الخمس:**
  1. عمود واحد `items.is_active` (boolean) ويه فهرس.
  2. scope صريح `Item::active()`. لا global scope، ولا اعتماد على المستخدم المسجل.
  3. الفلترة بس للاختيار والعرض: قوائم المواد، والبحث عند إضافة مادة لفاتورة أو أوردر، والتطبيق.
  4. السجلات المالية ما تنفلتر أبداً: علاقة `->item` ببند الفاتورة أو الدفعة أو الأوردر ترجع المادة دائماً.
  5. مسار كتابة واحد: كل تفعيل وتعطيل يمر من خدمة وحدة بيها كل الشروط.
- **وين تنستدعى `active()`:**

  | المكان | ينفلتر؟ |
  |---|---|
  | فهرس المواد (ويه فلتر "عرض المعطل" يشيل الشرط) | ✅ |
  | بحث المواد عند إنشاء فاتورة شراء أو أوردر | ✅ |
  | API التطبيق وقوائم البيع | ✅ |
  | صفحة تفاصيل مادة برابطها المباشر | ❌ |
  | علاقات `->item` من بنود الفواتير والدفعات والأوردرات | ❌ |
  | حساب المخزون والكلفة والتقارير المالية | ❌ |
  | الـ jobs الليلية | ❌، إلا إذا المقصود صراحةً استثناء المعطل |

- **خدمة الكتابة `ItemActivation`:**
  - `activate()` و `deactivate()`، و `deactivate()` تنادي `assertCanDeactivate()`.
  - كل شرط `if` مستقل يضيف رسالة، وبالنهاية ترمي `ValidationException` بكل الرسائل.
  - أمثلة شروطه: الرصيد مو صفر، أو فواتير معلقة، أو مبيعات خلال 48 ساعة.
  - إذا الشروط صارت أكثر من 5 تقريباً، كل شرط يصير class يطبق `DeactivationRule` (`check(Item $item): ?string`).
  - التعطيل الجماعي ينادي `deactivate()` لكل مادة، ويجمع المرفوضة ويا أسبابها، وما يتجاوز الشروط.
- **الممنوعات:**

  | الممنوع | ليش |
  |---|---|
  | global scope مربوط بالمستخدم المسجل | نفس الـ query تعطي نتائج مختلفة بالويب والـ jobs |
  | `loginUsingId(...)` داخل الـ jobs | الـ job يورث بيانات مستخدم ممكن تتغير |
  | فلترة علاقات `->item` بالسجلات المالية | ترجع `null`، فتنتخطى حسابات المخزون والكلفة بصمت |
  | نسخ شرط الفلترة كـ SQL خام بكل مكان | أي تعديل يحتاج تدور على كل النسخ |
  | تعطيل بـ `update()` مباشر أو من أكثر من مسار | الشروط وسجل التدقيق يتجاوزن |
  | تصفير الكمية أو تغيير المخزون عند التعطيل | يحرك قيمة المخزن والمطابقة المالية. الصحيح: **منع** التعطيل ويه وجود رصيد |
  | أكثر من معنى على نفس العمود | "فعال" غير "ظاهر أونلاين" وغير "ينشرى". كل معنى إله عمود |

- **الـ tests اللي يطلبها:**
  - `active()` يخفي المعطل ويعرض الفعال.
  - `invoiceItem->item` يرجع المادة وهي معطلة.
  - `deactivate` ينرفض لكل شرط لحاله ويرجع رسالته.
  - `deactivate` ينجح إذا ماكو ولا شرط، وينسجل بالتدقيق.
  - الـ job الليلي يمر على المعطل هم، إذا هذا المقصود.
- **إذا جا مصنع ثاني:**
  - جدول `factory_items` بيه (`factory_id`، `item_id`، `is_active`) ويه unique على (`factory_id`، `item_id`).
  - `active()` يصير `activeIn(int $factoryId)`.
  - الخدمة تاخذ `$factoryId`.
  - العلاقات والتقارير والـ jobs ما تتغير، لأنها أصلاً ما تنفلتر.

### 6.2 اللي يتفق ويا نقاشنا
- عمود واحد بدون تفعيل لكل مصنع، وخطة واضحة إذا جا مصنع ثاني.
- ممنوع ربط الفلترة بالمستخدم المسجل.
- علاقات السجلات المالية ما تنفلتر.
- مسار كتابة واحد بيه كل شروط التعطيل.
- منع التعطيل ويه وجود رصيد، بدل تصفير المخزون.
- كل معنى إله عمود.
- التعطيل الجماعي يطبق نفس الشروط ويرجع أسباب الرفض.

### 6.3 النواقص والمشاكل بالنسبة لمشروعنا
1. **ماكو حماية عند الحفظ بالفواتير.** الدليل يفلتر بقائمة الاختيار بس. إذا انسى `active()` أو انبعث الطلب يدوي، المنتج الغير فعال ينضاف. الحماية بالقسم 5 (الطبقة 2) تسد هالنقص.
2. **"لا أحد يكتب على العمود مباشرة" بدون شي يفرضها.** هاي نفس مشكلة النسيان. بمشروعنا هسه:
   - `is_active` بالـ fillable.
   - الفورم بيه Toggle يكتب مباشرة (القسم 2).

   طرق الفرض الممكنة:
   - نشيل `is_active` من الـ fillable.
   - نشيل الـ Toggle ونسوي أزرار تفعيل وتعطيل تنادي المسار الواحد.
   - tests تتأكد إن التعطيل ما يصير إلا منه.
3. **الكود مو على Laravel 13 ولا على أسلوب المشروع:**
   - `protected $casts` بدل `casts()` method.
   - `scopeActive()` بدل `#[Scope]`.
4. **الرسائل مكتوبة عربي داخل `__()`.** هذا يخالف قاعدة اللغتين (CLAUDE.md، القاعدة 3). لازم مفاتيح بـ `lang/ar` و `lang/en`، والإنكليزي افتراضي.
5. **شكل الخدمة يختلف عن نمط المشروع.** الدليل: class خدمة واحد `ItemActivation`. مشروعنا: Action class لكل عملية (القسم 2).
6. **الصلاحية ناقصة.** الدليل يحدد "متى ينسمح التعطيل"، مو "منو يكدر يعطل" (`item.update` لو `item.deactivate`).
7. **الفهرس على boolean:** بـ PostgreSQL قليل الفايدة إذا أغلب القيم `true`. إذا كبر الجدول، partial index أنسب.
8. **أشياء بعدها ما موجودة عندنا:** سجل التدقيق، الـ jobs الليلية، الفواتير، المخزون.
9. **نوع الـ tests:** الدليل يطلب integration، واتفاقنا unit أول وبعدين صاحب المشروع يطلع منها الـ integration (plan اليوزرز، القسم 4).

## 7. شروط التعطيل: وين تنكتب
| الخيار | الإيجابيات | السلبيات |
|---|---|---|
| **Policy ability `deactivate`** | يمشي ويا نظام الصلاحيات (plan اليوزرز 2.1)، فتطلع `item.deactivate` تلقائياً | يخلط "منو يكدر" ويه "متى يصير"، وما يرجع رسالة توضح سبب الرفض |
| **Action classes** (`ActivateItem` و `DeactivateItem`) | نفس نمط `SyncUserPermissions`، ويرجع رسائل مترجمة، وتستخدمه الشاشة والـ API، وسهل تكتبله tests | ملفات أكثر، ولازم كل تغيير لـ `is_active` يمر منه |
| **class خدمة واحد** (`ItemActivation`، مثل الدليل) | التفعيل والتعطيل وشروطهم بملف واحد | يختلف عن نمط المشروع |
| **Model event `updating`** | يمسك أي تغيير من أي مكان | الخطأ يطلع من الموديل فرسالته بالشاشة أصعب، والشروط تتخبى داخل الموديل |

- **التوصية المطروحة، مو محسومة:**
  - الـ Policy تحدد **منو** يكدر يعطل.
  - Action أو خدمة تحدد **متى** ينسمح التعطيل.
  - الشروط بمكان واحد بس، مو بالفورم ولا بزر معين.

## 8. أسئلة للحسم
1. **طريقة الإخفاء:** local scope (التوصية الحالية) لو global scope؟
2. **مسار التعطيل:** Action classes مثل اليوزرز، لو class خدمة واحد مثل الدليل؟ ووين مكانه (`app/Items`؟ `app/Actions`؟)
3. **الصلاحية:** يكفي `item.update` للتفعيل والتعطيل، لو نحتاج `item.deactivate` منفصلة؟
4. **التوقيت:** نشيل Toggle الفورم و `is_active` من الـ fillable هسه، لو لما تجي أول شروط تعطيل؟
5. **الاستخدام العام:** هل "فعال/غير فعال" راح يصير لموديلات ثانية؟ إذا نعم، نسوي trait عام (`HasActiveState`) ويه scope مشترك.
6. **الحماية عند الحفظ:** نثبتها هسه كقاعدة، حتى تنكتب ويه أول فاتورة أو أوردر؟
7. **فلتر الجدول:** نضيف فلتر "فعال/غير فعال" لجدول المنتجات بالأدمن؟
8. **الفهرس:** نضيف فهرس على `is_active` هسه، لو ننتظر لما يكبر الجدول؟
